B — intent classification (node 3)
4Intent classification
3-tier waterfall — first confident tier wins:
Semantic router
embed(query) → cosine vs anchor phrases · min_score=0.42 AND margin≥0.12 → fast, deterministic, ~50× cheaper than LLM
LLM supervisor
reads routing_description per agent from agents.yaml · handles paraphrases and compound queries
Keyword fallback
whole-word match on trigger_keywords · runs if LLM call fails for any reason
Router is ~50× faster and deterministic; LLM handles ambiguous/out-of-distribution; keywords are the safety net
C — agent execution (nodes 4–8, one agent per query)
5Hybrid RAG retrieval
embed(query) → Qdrant pre-filter (project + stale=False) → vector top-30 + BM25 on same corpus → RRF(k=60) → cross-encoder rerank (ms-marco sigmoid T=3) → top-7 parent chunks + confidence score
Corrective RAG loop fires if confidence <0.45 — LLM reformulates query → retry → best of two
Hallucination guardguard
if confidence < 0.20 (_LOW_CONFIDENCE_THRESHOLD) → abort agent → return "insufficient evidence" response immediately
Irrelevant chunks are often returned for out-of-domain queries — the LLM would hallucinate from training data without this gate
Exit path: response → persona adapt → user (skips LLM generation)

D — post-processing (nodes 9–10)
HITL gatewrite actions only
if hitl_required=True → hitl_manager.save(proposal) → Redis TTL 24h (SQLite fallback) → return hitl_action_id · frontend shows Approve / Reject buttons · POST /api/hitl/approve|reject resolves the pending action
Write-capable MCP tools (create ticket, assign reviewer) always require human approval before execution — LLM proposes, human confirms
Skip persona checkguard
if skip_persona=True OR response contains signals ("does not exist in jira", "already assigned to", "no action needed") → skip to response · also skip if agent sets skip_persona explicitly
Short factual corrections ("ticket SDLC-99 does not exist") lose meaning when rewritten into stakeholder language — preserve them verbatim
9Persona adaptation
2nd LLM call — ONLY job: rewrite tone for user role (developer / manager / technical_leader / stakeholder) · strict rules: keep all facts, ticket IDs, numbers exactly — only vocabulary and emphasis change
One LLM call can't simultaneously reason over 7 RAG chunks AND write in stakeholder tone — splitting produces cleaner role-specific language (+3–5s latency, accepted for demo)
Faithfulness evaluationeval gate
if NOT using MCP data AND confidence < reflect_faithfulness_threshold (0.45) → LLM-as-judge: reads top-6 chunks + response → flags unsupported claims → returns {supported_claims, unsupported_claims, score} JSON
MCP answers are skipped — judge scores them low even when correct because live data isn't in rag_chunks · fails open (1.0) on error so judge failure never suppresses a legitimate answer
Reflect and revise loopone retry only
if faithfulness < 0.45 → regenerate from evidence only (no MCP, no memory) → persona-adapt the revision → re-score faithfulness · keep revision ONLY if new score > original — can never make answer worse · degrades to original on any error
Catches hallucinations that slipped past the low-confidence guard — model added a training-data fact the retrieved chunks don't support
E — output + telemetry
10Response returned + metrics saved
Stream response to user · append to eval_results.jsonl: precision (context P), recall (context R), faithfulness, answer_relevancy (embed cosine), answer_correctness (0.5 factual + 0.5 semantic), intent_accuracy · composite = 0.20P + 0.20R + 0.25F + 0.15Rel + 0.20Cor
5 independent metrics catch different failure modes: precision = retrieval noise, recall = missed facts, faithfulness = hallucination, relevancy = topic drift, correctness = wrong answer despite good retrieval
