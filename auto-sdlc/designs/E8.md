# E8 — HITL approval UX: per-action scopes (Approve / Approve-all / Reject)

## Problem
Every HITL proposal shows the same two buttons — Approve / Reject — no matter
how risky the action is. A manager running several sprint-status broadcasts
in one conversation (`notify the managers: ...` → `send_slack` proposal) has
to click Approve on an identical-shape, low-risk, reversible action every
single time. Research on 2026 HITL approval-gate UX confirms this is the
known failure mode ("approval fatigue" — reviewers start clicking Approve
without reading once every action, regardless of risk, requires the same
click) and that the current standard fix is a **risk tier**: safe actions run
freely, *risky* actions get a one-time "always allow for this session"
approval, *destructive* actions always ask individually.
[Human-in-the-Loop Tool Calling: Approval Gates for AI Agents](https://www.scalekit.com/blog/human-in-the-loop-tool-calling) ·
[Human-in-the-Loop AI Agents: Approval Gate Design](https://cogniqai.ai/blog/human-in-the-loop-ai-agent-approval-gates-2026)

The backlog's own decision matrix (already drafted) puts exactly one action
type in the "approve-all eligible" tier today: `send_slack` (Slack/Teams
notify — low-risk, reversible-ish). Everything else (ticket create/edit,
reviewer assign, PR approve/reject, release GO) stays Approve/Reject-only,
every time — matches the 2026 pattern's "destructive always asks" tier.

## SDLC phase
Operate — this is pure HITL-governance UX, not a new agent capability.

## User flow
1. `NotifyAgent` proposes a `send_slack` HITL action (unchanged).
2. The HITL card now shows a 3rd button, **only** for action types on the
   approve-all-eligible list: **✅ Approve · ✅ Approve all (this chat) · ❌ Reject**.
3. **Approve** — executes once, exactly as today. No scope change.
4. **Approve all (this chat)** — executes this one action (same backend call,
   `remember=true`) AND remembers, client-side, that this browser tab's
   conversation has opted in to auto-approving this action type.
5. Any later `send_slack` proposal in the same conversation: the HITL card
   detects the remembered opt-in on mount and calls Approve automatically —
   no buttons shown, no click needed — then posts the result with a small
   "(Auto-approved for this conversation)" note so the user still sees it
   happened.
6. Reload the page / start a new session → the opt-in is gone (scoped to
   "this conversation", not persisted) — matches the research pattern's
   session-scoped tier, not "always allow forever".

## Where the scope actually lives (and why)
The eligibility list and the "remembered" state both live **client-side**
(`HitlService`, a `providedIn: 'root'` singleton — lives exactly as long as
the browser tab's conversation does). Considered and rejected a backend
Redis-backed session flag (mirroring `HITLManager`'s own pattern): it would
require the `check_hitl` orchestrator node to auto-execute the write itself,
duplicating the entire action-dispatch `if/elif` chain that already lives in
`backend/api/routes/hitl.py` (role checks, MCP calls, episodic memory,
session-store updates) — a second copy of that logic is a correctness risk
for no behavioral gain, since the *existing* `/api/hitl/approve` call already
does everything needed the moment the frontend decides to fire it
automatically. The eligibility list itself is a static UX/policy constant
(which action types are "low-risk"), not a probabilistic agent decision — P1
("no hardcoded rules") governs *agent* decisions (routing, retrieval,
duplicate detection); a fixed risk-tier list is the same kind of static
policy value the rest of the app already keeps in config, just small enough
(one entry) that a config file would be ceremony over substance for now.

`remember=true` is still sent to the backend on the one call that sets the
opt-in — not for authorization (the backend doesn't gate on it; the role
check via `require()` already runs on every approve regardless of scope) but
so the episodic-memory audit trail records *which* approvals were "approve
once" vs. "approved for the rest of this session", per the research note's
audit-trail requirement.

## API / schema changes
- `HITLRequest.remember: bool = False` (new, optional) — audit-trail marker
  only; execution and authorization are unaffected either way.
- `ChatResponse.hitl_action_type: str | None = None` (new) — the proposal's
  `action` field, so the frontend can decide whether to offer Approve-all
  without re-deriving it from the response text. `None` whenever
  `hitl_required` is `False`.
- `backend/api/routes/hitl.py` `approve_hitl`: when `remember=True`, the
  episodic-memory record text and log line note "(remembered for this
  session)" — no other behavior change.

## UI states
- Normal: Approve / Reject (unchanged) — action type not on the eligible list.
- Eligible, not yet opted in: Approve / Approve all (this chat) / Reject.
- Eligible, already opted in this conversation: card skips straight to a
  busy spinner (reuses the existing `busy` state / spinner markup — no new
  loading state), then resolves with the auto-approved note. If the
  auto-approve call itself fails (e.g. the action expired server-side before
  the client got here), falls back to the existing error-banner path, which
  already re-shows the normal buttons on non-404 errors.
- Error / 404 paths: unchanged (existing `onActionError` handling covers the
  new button the same way it covers the existing two).

## Accessibility / motion
No new animation — the 3rd button reuses the existing button styling and the
card's existing entrance animation (`E12` slice 1, `prefers-reduced-motion`
already respected globally). The auto-approve spinner reuses the existing
`mat-spinner`.

## Acceptance criteria
- A `send_slack` HITL card shows 3 buttons; every other action type (ticket
  create/edit/comment/assign, reviewer assign, PR approve/reject, release
  approval) shows only 2 — no behavior change for those.
- Clicking "Approve all" executes the action (identical result to Approve)
  and causes every *subsequent* `send_slack` proposal in the same browser
  tab's conversation to auto-resolve with no click.
- A fresh page load (new `HitlService` instance) does not carry over any
  prior tab's auto-approve state.
- `remember=true` has zero effect on whether the action is authorized or
  what it executes — only the audit-trail text differs.
- `hitl_action_type` is `None` on every response where `hitl_required` is
  `False`, and matches the proposal's `action` otherwise.

## Test plan
- Backend: `tests/unit/test_chat_hitl_action_type.py` — `hitl_action_type`
  present and correct when a proposal exists, `None` otherwise (mirrors the
  existing `_build_trace` pure-function test pattern in `test_chat_trace.py`).
- Backend: extend `tests/unit/test_hitl_assign_reviewer.py`-style route test
  (new file) — `remember=true` adds the "(remembered for this session)" note
  to the episodic-memory call; `remember` omitted/false does not; the actual
  executed result text is identical either way.
- Frontend: `hitl-card.spec.ts` (new — first spec for this component):
  1. Approve-all button renders for an eligible `actionType`, not for others.
  2. Clicking Approve-all calls the service with `remember=true` and marks
     the action type auto-approved on success.
  3. A card mounted with an already-auto-approved `actionType` calls Approve
     immediately with no buttons rendered.
  4. A card for a non-eligible `actionType` never auto-approves even if some
     *other* action type was previously marked.
