# E7 — Deassign a Jira ticket (edit/delete close-out)

## Problem
`REDESIGN_BUGS.md` E7 ("Edit/delete ticket + deassign") has stood open for weeks behind a
design question that no longer applies: how does a user reference *which* entity in natural
language? `ticket_agent.py` already solved that generically for assign/edit/comment (B10's
`_last_ticket_id_from_history`). Re-reading the code found E7 is two-thirds done and
mis-tracked (the same stale-narrative pattern as B1/B2/B4/B5/B7a/B7b/E3/E4/B9):

- **Edit** (title/description) — already shipped (`_run_edit_ticket`, `edit_ticket` HITL
  action, permission row). Not previously credited.
- **Delete** — deliberately **not** supported. `permissions.py`'s own docstring (2026-07)
  already removed `delete_ticket` from the matrix: no MCP tool, no connector method, no
  agent/HITL wiring — a pure aspirational entry. This matches the backlog's own caution
  ("real Jira delete is destructive") and the open question C5 ("real delete vs
  close/cancel?"). **Decision (today): keep it unsupported.** Jira's own UI/workflow is the
  right place for a destructive, audit-sensitive operation like issue deletion; this
  assistant's HITL model is built for propose→approve on a known, reversible action set, not
  for "are you really sure" irreversible deletes. Closing ticket should go through a Jira
  status transition (not modeled here — no request for it, not building speculatively).
- **Deassign** — the one real gap. `ticket_agent.run()`'s intent regexes are
  `\b(assign|reassign)\b` (assignment) and no branch at all matches "deassign"/"unassign"
  (word-boundary regex correctly does NOT match the embedded substring "assign" inside
  "deassign"/"unassign" — so today "deassign SDLC-5" falls through every branch and lands in
  the ticket **CREATE** flow, same bug class B10 fixed for assign/edit/comment).

## SDLC phase
Build/operate — a developer/manager clearing a stale assignment (e.g. someone left the
sprint, or a ticket was assigned to the wrong person and needs to go back to the backlog
before reassigning).

## User flow
1. User: "deassign SDLC-5" / "unassign SDLC-5" / "remove the assignee from SDLC-5".
2. `ticket_agent` resolves the ticket ID (explicit or from `recent_messages`, same rule as
   assign/edit/comment), fetches the ticket over MCP.
3. Already unassigned → no-op message, no HITL (mirrors `_run_assignment`'s "already assigned
   to X" short-circuit).
4. Otherwise → HITL proposal card showing current assignee → "(unassigned)".
5. Approve → Jira issue's `assignee` cleared via `PUT /issue/{key}/assignee` with
   `{"accountId": null}` — Atlassian's documented null-unassign contract for both REST API v2
   and v3, unchanged since Jira Cloud API's introduction. Reject → cancelled, ticket untouched.

## API / MCP / schema changes
- **Connector** (`sdlc-mcp-server/connectors/jira_connector.py`): new
  `deassign_ticket(ticket_id) -> dict`, same shape as `assign_ticket` but posts
  `{"accountId": None}`. Not folded into `assign_ticket(ticket_id, account_id)` — that method's
  one caller always passes a real id; overloading "empty string" to mean "unassign" would make
  that call ambiguous with "couldn't resolve a name" (see hitl.py note below).
- **MCP tool** (`sdlc-mcp-server/tools/jira_tools.py`): new write tool `jira_deassign_ticket
  (ticket_id: str) -> dict`, same `_invalid_ticket_id` boundary check as the other ticket
  write tools. Registered in `register_writes`.
- **Permission** (`backend/auth/permissions.py`): new action `deassign_ticket`, same tier as
  `assign_ticket` (developer/manager/technical_leader/admin; not stakeholder — matches the
  capability matrix's "Assign / reassign / deassign" row at the top of `REDESIGN_BUGS.md`).
  Falls into `ALL_ACTIONS` → automatically included in `_FULL_NO_RELEASE`/`ALL_ACTIONS`; the
  stakeholder's explicit allow-set is untouched (still excluded). Zero matrix-logic changes.
- **Agent** (`backend/agents/ticket_agent.py`): new intent branch (checked alongside
  assign/edit/comment, before the generic LIST/CREATE fallthrough) matching
  `\b(deassign|unassign)\b` or "remove (the )?assignee" → `_run_deassignment(state, ticket_id)`.
  Reuses `resolved_ticket_id` (history-aware) already computed in `run()`.
- **HITL execution** (`backend/api/routes/hitl.py`): new action type `"deassign_ticket"` →
  `_execute_deassign_ticket(proposal, approver_name)` calling `jira_deassign_ticket` via the
  existing `_mcp_write` helper (same pattern as `_execute_edit_ticket`). New reject-text branch.
  A **new action type**, not an overload of `assign_ticket` with `account_id=""` — that string
  is already overloaded to mean "named target not found" in `_run_assignment` (which returns
  early, no HITL, for that case) and "not executed" in `_execute_assign_ticket`'s `if
  account_id:` guard. Reusing it for "intentionally unassign" would make a currently-unambiguous
  empty-string check lie three different ways; a dedicated action type costs one frozenset
  entry and is the honest fix.

## UI states
No frontend changes needed. The HITL card renders generically from the proposal's markdown
`final_response` text + Approve/Reject (not in `APPROVE_ALL_ELIGIBLE` — deassign is a real Jira
write, not the "low-risk notify" tier E8 defined approve-all for). Loading/empty/error states
are the existing generic HITL-card/chat states, unchanged.

## Acceptance criteria
- "deassign SDLC-5" / "unassign SDLC-5" with an existing assignee → HITL proposal, approve →
  Jira assignee cleared, Jira's own PUT payload is `{"accountId": null}`.
- Already-unassigned ticket → short message, no HITL, no Jira call.
- No ticket ID anywhere in query or history → asks which ticket (not a bogus CREATE proposal).
- Stakeholder role → 403 at the HITL execution layer (`require()`), same as every other team
  write action.
- "deassign"/"unassign" queries that used to fall into ticket-CREATE are now caught upstream of
  that fallthrough.
