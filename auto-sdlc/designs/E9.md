# E9 — "Why this answer?" decision-trace panel

Backlog ref: `ai-sdlc-assistant/REDESIGN_BUGS.md` §B/E9 (🟠 Frontend explainability).

## Problem

The chat UI already shows aggregate chips (agent / strategy / confidence / faithfulness) but
gives no way to see *why* the assistant answered the way it did: which MCP tools it called,
whether they succeeded, and which RAG chunks (with scores) backed the answer. Users have to
log-dive to check the assistant's reasoning — bad for trust, bad for demoing the agentic parts.

## SDLC phase

Cross-cutting observability — applies to every query, most valuable during **review** (a
manager checking "did it actually check Jira, or make this up?") and **operate** (debugging a
wrong answer).

## What already exists (audited before writing this)

- `backend/orchestrator/classifier.py::llm_classify()` already asks the LLM for a `reason`
  string and logs it — then throws it away. Never reaches state or the response.
- `backend/agents/mcp_agent.py::MCPAgent.run()` already returns, per query,
  `structured["mcp_calls"]` (tool name / args / error) and `structured["rag_chunks"]`
  (text / source / score) inside its `AgentPayload`. Computed for every MCPAgent-served query,
  dropped before `chat.py` builds `ChatResponse`.
- Specialist agents (ticket / risk / pr_review / release_readiness / notify) don't populate
  `mcp_calls` — they have fixed tool needs, not LLM-picked ones — so trace will be routing-reason-only
  for those, which is correct, not a bug.

So this is a **wiring** feature, not new intelligence: surface data the backend already computes.

## User flow

1. User asks a question that resolves to `cross_source` → `MCPAgent` (e.g. "what's blocking the
   dashboard, and what's in the latest PR?").
2. Assistant streams the answer as today; the existing meta-chip row appears (agent, strategy,
   confidence, faithfulness, sources).
3. A new **"Why this answer?"** disclosure appears directly under the meta-chip row, collapsed by
   default. Expanding it shows:
   - Routing reason (one line — why the supervisor picked this agent).
   - Tools called (name + ✅/❌), if any ran.
   - Top RAG chunks used (source + relevance score), if any were retrieved.
4. If none of the three exist (e.g. a blocked/refused query, or a HITL proposal card), the
   disclosure doesn't render at all — nothing to explain.

## API / schema changes

- `backend/orchestrator/classifier.py::llm_classify()` — return `(agents: list[str], reason: str)`
  instead of `list[str]`. `keyword_classify()` path has no LLM reasoning, so its reason is `""`.
- `backend/orchestrator/state.py::SDLCState` — add `routing_reason: str`.
- `backend/orchestrator/nodes.py::classify_intent()` — capture and return `routing_reason`.
- `backend/api/routes/chat.py` — build a small `trace` dict from `result["routing_reason"]` +
  `agent_payloads[*].structured["mcp_calls"/"rag_chunks"]` (same extraction pattern already used
  there for `images`), omit it entirely (`None`) when there's nothing to show.
- `backend/api/models/schemas.py::ChatResponse` — new optional field:
  `trace: TraceInfo | None = None` where `TraceInfo` = `{routing_reason: str,
  tools_called: list[{tool: str, ok: bool}], top_chunks: list[{source: str, score: float}]}`
  (top 5 chunks by score, tools deduped by name).
- Angular `api.models.ts` — mirror `TraceInfo` on `ChatResponse` and `ChatMessage`.

## UI states

- **Absent** (nothing to explain): no disclosure rendered — not even an empty collapsed one.
- **Collapsed** (default): a single-line `<summary>` — "Why this answer?" — sits right after the
  existing `.bubble-meta` chip row, same left margin as the bubble text.
- **Expanded**: routing reason as a line of body text; tools-called and top-chunks each as a
  small bulleted list, visually subordinate to the bubble text (smaller size, muted color) —
  same visual weight class as the existing `.confidence` / `.source-chip` chips, not a new loud
  block.
- No loading state needed — the trace arrives with the same `ChatResponse` as everything else,
  never streamed separately.

## Component choice (deliberately minimal)

Native `<details>`/`<summary>` — no new Angular Material component, no JS toggle state, free
keyboard/screen-reader support (it's a standard disclosure widget). This matches the existing
codebase's "thin client" rule and the ladder: a native platform feature beats a component import
for a single collapsible block. Styling only (see mockup) — `ai-sdlc-assistant/frontend-angular/src/app/chat/chat.css`
already defines the exact chip palette (`.source-chip`, `.confidence`, `.faith-chip`) this panel
reuses rather than inventing new colors.

Mockup: `auto-sdlc/designs/E9.html` (static, hand-built against the existing chat.css palette —
Stitch/Claude Design tools aren't available in this environment, and running the `impeccable`
skill's full init/context pipeline was skipped as disproportionate for a single disclosure
widget that reuses an established chip system one file away; the guidance below was pulled from
`impeccable`'s general typography/spacing rules instead).

Guidance applied: `<summary>` styled like the existing `.confidence` chip (0.75rem, muted, not a
button); expanded content indented to align with bubble text, 4px vertical rhythm between the
three sub-sections, no side-stripe borders (the skill's own anti-pattern list — this codebase
doesn't use them either), tool/chunk lists as flat `<ul>` with 0.75rem lines matching `.source-chip`
text size so the panel doesn't out-weigh the answer above it.

## Acceptance criteria

- A `cross_source` query that triggers at least one MCP tool call shows routing reason + tool
  list + chunk list (when RAG also ran).
- A pure-RAG query (no MCP call) shows routing reason + chunk list, no "Tools called" section.
- A blocked / HITL-proposal / no-evidence response shows no disclosure at all.
- All three existing gates (`pytest` backend, `pytest` MCP server, `ng test` + `ng build`) stay
  green; no existing test is weakened to pass.

## Test plan

- Backend: `tests/unit/test_classifier.py` — `llm_classify` returns the LLM's reason string on a
  successful structured response, and `""` on the keyword-fallback path.
- Backend: `tests/unit/test_chat_trace.py` (or inline in existing chat route test file) — the
  trace-building helper returns `None` for an agent_payloads list with no mcp_calls/rag_chunks,
  and a populated `TraceInfo` when they're present, deduping tool names and capping chunks at 5.
- Angular: `chat.spec.ts` (or a new small spec) — the `<details>` panel is absent when
  `msg.trace` is undefined, and renders routing reason / tool / chunk lines when present.
