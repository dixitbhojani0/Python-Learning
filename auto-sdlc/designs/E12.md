# E12 — Product-grade motion system (slice 1: tokens + chat entrances + streaming caret)

Backlog ref: `ai-sdlc-assistant/REDESIGN_BUGS.md` §B/E12 (🟠, **requested**). E12 is large ("Big
ones can span several days" per the daily-run brief) — this is slice 1, shipped and tested today;
remaining scope stays ◐ in the backlog.

## Problem

The chat UI has zero motion: messages pop into the list, the HITL approval card appears with no
transition, and there's no visual signal that tokens are still streaming in vs. the answer being
final. Enterprise chat products use motion specifically to communicate state (streaming, pending
approval) — its absence here isn't neutral, it's a missing signal.

## SDLC phase

Build/UI polish, cross-cutting — improves every chat turn, most visible during **review** (a
demo) and daily use (developer/manager/stakeholder chat sessions).

## Research before starting (per E12's own note + engineering standards)

- **Angular native animations** (`angular.dev/guide/animations`, fetched today): `animate.enter` /
  `animate.leave` are stable since **v20.2** (we're on Angular 21.2) and are the Angular-team
  recommended replacement for `@angular/animations`, which is now deprecated for new code. Syntax:
  `animate.enter="css-class"` (static) or `[animate.enter]="expr()"` (dynamic); the class must
  itself carry a CSS `animation` or `transition`; Angular removes the class once the
  animation/transition finishes. **`prefers-reduced-motion` is not handled by the framework** —
  confirmed explicitly not covered, must be handled in our own CSS.
- **Audit: no legacy animations to migrate.** Grepped the whole `frontend-angular/src` tree for
  `trigger(`/`@angular/animations` imports — zero hits. The only `@angular/animations`-adjacent
  code is `provideAnimationsAsync()` in `app.config.ts`, which is Angular Material's animation
  provider (needed for Material component internals, e.g. ripple/overlay), not our own
  trigger/state/transition code. Nothing to migrate off for this slice.
- **GSAP license** (checked live, not from memory — it changed in 2025): as of **April 2025**,
  Webflow sponsors GSAP and **all plugins (Flip, SplitText, ScrollTrigger, MorphSVG, etc.) are
  100% free**, including commercial use — the old "Club GSAP" paywall is gone. Relevant for later
  slices; **not added as a dependency in this slice** (see "What's deferred" — nothing here needs
  more than CSS + native `animate.enter`, so pulling in `gsap` now would be an unused dependency).

## User flow (this slice)

1. A new chat message (user or assistant) appears in the list → fades/rises in briefly instead of
   popping in.
2. While the assistant's answer is still streaming (tokens arriving, answer not yet finalized), a
   blinking caret sits at the end of the text — disappears the instant the final `ChatResponse`
   replaces the streamed draft.
3. A HITL approval card appears (after a risky-action proposal) with a slightly more deliberate
   entrance than a chat bubble, since it demands the user's attention and appears far less often.
4. A user with `prefers-reduced-motion: reduce` set at the OS level sees none of the above as
   motion — the global stylesheet neutralizes all animation/transition durations to effectively
   instant, everywhere, present and future (see "Accessibility" below).

## Motion judgement (via `emil-design-eng` skill)

Consulted before picking durations — key inputs applied:
- **Frequency test**: chat bubbles appear on *every* message (high frequency) → per the skill's
  own table this sits at "remove or drastically reduce," not a showcase entrance. Kept **short**
  (120ms, the "fast" token) and subtle (opacity + 4px rise, no bounce/scale).
- HITL cards appear **occasionally** (once per risky action) → standard entrance is appropriate:
  200ms ("base" token), opacity + scale(0.95→1) + slight rise — matches the skill's explicit rule
  "never animate from scale(0)."
- **Easing**: entering elements → `ease-out` (starts fast, feels responsive) per the skill's
  decision tree; never `ease-in` for UI.
- **One-shot vs. interruptible**: bubbles and the HITL card each mount once and stay — no
  rapid add/remove cycles — so plain `@keyframes` is simpler than the CSS-transition +
  `@starting-style` pattern (which exists specifically for elements that can be
  re-triggered/interrupted, e.g. stacking toasts). Keyframes were chosen deliberately for that
  reason, not as an oversight.
- **Streaming caret**: continuous while active — a simple `step-end` blink (matches a terminal
  cursor), not a decorative animation. Failure mode to avoid: anything flashier competes with the
  actually-changing text next to it. A plain 1s opacity blink is the least distracting option that
  still reads as "still working."

## Shared tokens

`frontend-angular/src/styles.css` (global — the project has no `src/styles/` directory yet and
adding one for three custom properties would be structure for structure's sake):
```css
:root {
  --motion-fast: 120ms;
  --motion-base: 200ms;
  --motion-ease-out: cubic-bezier(0.23, 1, 0.32, 1);
}
```
Two durations, one easing — the third token (a "slow" tier) is deferred until a component actually
needs it (modals/drawers in a later slice); adding an unused token now is speculative.

## Accessibility (non-negotiable per E12 acceptance)

Global kill-switch in `styles.css`, the standard WCAG-safe pattern (not a per-component check):
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```
Deliberate design choice over a per-component `MotionService.prefersReducedMotion()` check: **one
guard that covers every current and future CSS animation**, vs. N call sites that each have to
remember to check. The `emil-design-eng` skill notes reduced-motion should ideally keep
opacity/color transitions and only strip movement — this blanket rule instead neutralizes
everything uniformly, which is the simpler, safer default for a one-day slice; a future slice can
special-case something back in if a specific transition is judged essential under reduced motion.
No component ends up broken either way — the caret still renders (just static, no blink), bubbles
and the HITL card still appear (just without the fade/rise).

## Where motion goes (this slice only)

- `frontend-angular/src/app/chat/chat.html` / `chat.css`: `.bubble` gets
  `animate.enter="bubble-enter"`; a `.stream-caret` span renders after the markdown body only when
  `last && loading()` is true (i.e. the assistant's final message is still being streamed).
- `frontend-angular/src/app/chat/hitl-card/hitl-card.html`: `mat-card.hitl-card` gets
  `animate.enter="hitl-enter"`.

## Acceptance criteria (this slice)

- New chat messages (user and assistant) fade/rise in on append; no layout jank scrolling a long
  thread (transform+opacity only, no layout-triggering properties).
- A blinking caret appears after the assistant's text while `loading()` is true for the last
  message, and disappears once the final response replaces the streamed draft.
- The HITL card fades/scales in when it first renders.
- `prefers-reduced-motion: reduce` removes all motion above (verified structurally — see test
  plan) without breaking any element's final visible state.
- All three gates stay green (`pytest` backend, `pytest` MCP server, `ng test` + `ng build`); no
  existing test weakened.
